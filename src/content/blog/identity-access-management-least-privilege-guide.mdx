Analysis of Verizon's 2026 Data Breach Investigations Report found vulnerability exploitation overtaking stolen credentials as the leading initial access vector for the first time in the report's history. But initial access is only the first step of an intrusion — what an attacker can actually do once they're in depends heavily on how much standing access the compromised account or exploited system already had. A foothold on an account with narrowly-scoped permissions is a contained incident. The same foothold on an over-permissioned account is a far larger one.

Identity and access management (IAM) is the discipline of making sure that gap — between "an attacker got in somewhere" and "an attacker now has broad access" — stays as small as possible. For a company without a dedicated identity team, that sounds like enterprise overhead. In practice, the core of it is a handful of disciplined habits.

## The core principle: access matches current need, not historical convenience

Least privilege means a user or system has exactly the access required for their current role and tasks — no more, "just in case," and no residual access left over from a role they used to have. It sounds obvious stated that way. In practice, access tends to accumulate rather than stay current: someone gets temporary admin rights for a one-off project and keeps them, a departed contractor's account gets disabled but not actually reviewed for what it had access to, a team member moves departments and picks up new permissions without losing the old ones.

None of this happens through negligence, specifically — it happens because tightening access requires deliberate, recurring effort, while leaving it alone requires none. That asymmetry is exactly why IAM needs to be a scheduled habit, not a one-time project.

## Role-based access control: the practical starting point

Role-based access control (RBAC) means permissions are assigned to roles (e.g., "finance," "developer," "support agent"), and individuals are assigned to roles — rather than granting permissions to each person individually, one request at a time. For a small company, this doesn't require a formal identity platform to implement meaningfully:

1. **List your actual roles** — not job titles, but distinct access patterns. A "finance" role and an "operations manager" role might need genuinely different system access even if one person currently holds both.
2. **Define what each role needs**, deliberately, rather than reverse-engineering it from whatever the current person in that role happens to have.
3. **Assign people to roles**, and audit for anyone whose individual access has drifted from what their role actually defines.

The value isn't the formal structure for its own sake — it's that RBAC makes "does this person have access they shouldn't" a question you can actually answer by comparing their access to a defined baseline, instead of having to reconstruct from memory whether a specific permission still makes sense.

## Periodic access reviews: the habit that actually matters most

A one-time access cleanup is useful. A recurring review is what prevents the same drift from re-accumulating within a year. A realistic cadence for a small-to-mid-size business:

- **Quarterly review of high-privilege accounts specifically** — admin accounts, financial system access, source-code repository access, anything that could cause significant damage if misused or compromised.
- **Annual review of everything else.**
- **Immediate review triggered by a role change, department move, or departure** — not folded into the next scheduled review, since the gap between a role change and an access update is exactly when stale access tends to persist longest.

A review doesn't need to be exhaustive to be useful. The question worth asking for each account, every time: "does this specific access still match what this person currently does?" — not "has anything gone wrong with this account," which is a much harder question to answer and not the point of a routine review.

## Just-in-time access for elevated permissions

Standing admin access — permissions that are always active, whether or not they're being used at a given moment — is the single highest-leverage thing to reduce. Just-in-time (JIT) access flips this: elevated permissions are granted for a specific task, for a limited window, and expire automatically (or get manually revoked) afterward.

A small team doesn't need a dedicated JIT platform to get most of the benefit. A documented process — "request temporary admin access for this specific task, get it approved, and it's reviewed or revoked within an agreed window" — captures the core principle even as a manual workflow. The goal is reducing how long elevated access exists unused and unmonitored, not building elaborate tooling around it.

## Offboarding: where access hygiene most often fails

Account offboarding is where IAM discipline is tested hardest, because it has a hard deadline (someone's last day) and competes with everything else happening around a departure. A practical offboarding checklist, run every time, regardless of how the departure happened:

- Disable the account across every system it had access to — not just the primary email or identity provider, if access was granted individually elsewhere.
- Revoke API keys, personal access tokens, and any credentials issued specifically to that person.
- Remove the person from any shared accounts or shared credential stores.
- Reassign or transfer ownership of any systems, domains, or accounts they administered.
- Confirm removal, don't assume it — a disabled login doesn't guarantee every access path (a forgotten API token, a forwarding rule they set up) is actually closed.

A departure that happens on bad terms makes this more urgent, not optional — but the checklist should be the same either way, since a routine resignation is just as capable of leaving stale access behind as a contentious one.

## IAM checklist for teams without a dedicated identity function

- [ ] Define roles based on actual access needs, not job titles
- [ ] Review high-privilege accounts (admin, finance, source control) quarterly
- [ ] Review all other accounts at least annually
- [ ] Trigger an immediate access review on every role change or departure
- [ ] Use a documented (even manual) process for temporary elevated access requests
- [ ] Maintain a specific, repeatable offboarding checklist covering every system, not just the primary login
- [ ] Confirm offboarding actions actually took effect — don't assume

## Key takeaways

With vulnerability exploitation now the leading initial access vector, what matters most after that first foothold is how far an attacker can move from it — and that is a direct function of how much standing access accounts actually hold. Least privilege, applied through defined roles, recurring access reviews, just-in-time elevation for admin tasks, and a disciplined offboarding checklist, meaningfully limits that blast radius — and none of it requires a dedicated identity team to start.
