# Learn with Shahid — Architectural Decisions Record

**Status:** approved project direction, as of 2026-09-27. These are locked decisions, not proposals — Phase 1 documentation (`lms-architecture.md`, `lms-database.md`, `lms-security.md`, `lms-payments.md`, `lms-business-model.md`, `lms-roadmap.md`, `lms-admin-guide.md`, `lms-student-guide.md`, `lms-deployment.md`) is approved as the technical detail behind them. **Approval of direction is not approval to build.** No infrastructure, database, or credentials are provisioned until you say "START PHASE 2," per `LMS_IMPLEMENTATION_PLAN.md`.

Each entry: the decision, and why. Numbered to match the approval message this record was created from, so either document can be cross-referenced from the other.

| # | Decision | Rationale |
| --- | --- | --- |
| 1 | Learn with Shahid is a **separate LMS application**, not an extension of the existing static site. | The existing site is static with no server runtime (`lms-architecture-audit.md`). A multi-user, stateful, payment-processing app needs a real backend; bolting one onto a static-site generator would fight the platform and put the marketing site's SEO/CSP/deploy pipeline at risk. Separation makes "don't damage the existing site" true by construction. |
| 2 | LMS application stack: **Next.js + PostgreSQL**. | Same language (TypeScript) as the existing site; mature ecosystem for auth/RBAC/payments; Postgres gives the relational integrity enrollments/payments/RBAC need. Detailed in `lms-architecture.md` §2. |
| 3 | Primary LMS domain: **`https://learn.shahidiqbal.com`**. | Keeps the product clearly part of the Shahid Security brand as a subdomain, without touching the main domain's existing DNS records, hosting, or deploy pipeline. |
| 4 | The existing `shahidiqbal.com` website remains the primary marketing, SEO, cybersecurity-services, and content site. | It already does this job well and was recently SEO-hardened; the LMS is a new product line, not a replacement for the consulting business's site. |
| 5 | The existing site receives new public SEO/marketing pages: `/learn`, `/learn/roadmap`, `/learn/courses`, `/learn/pricing`, `/learn/faq`. | These are genuinely static, indexable pages that explain the product and funnel visitors to the LMS app — they inherit the existing site's SEO infrastructure (sitemap, schema graph, CSP) for free, per `lms-architecture.md` §3 and §6. |
| 6 | The existing website is **not** migrated to Next.js unless a future, separate, explicit decision is made. | The static Astro site is not the bottleneck — the LMS's need for accounts/database/payments is. Migrating a working, SEO-hardened site for no functional reason would be pure risk with no benefit. |
| 7 | The existing production website architecture is **not modified** beyond the new static `/learn/*` pages. | Same reasoning as #1 and #6 — the marketing site's build, CSP, and deploy pipeline stay untouched; every LMS integration point is additive (new static pages, a new subdomain), never a change to what already works. |
| 8 | Initial product: **"Learn with Shahid Enrollment," PKR 800**, price stored as configurable product data, never hardcoded. | Satisfies the brief's explicit "prices update by country/location" and "don't hardcode PKR 800" requirements. Modeled as one row in `products` + one row in `prices` (`lms-database.md`) — changing the price later is a data edit in the admin, not a code deploy. |
| 9 | Enrollment grants: student account, student dashboard, cybersecurity roadmap, eligible learning resources, Discord community, Facebook group, Telegram group, member announcements. | This is the V1 membership product's `access_rules` (`lms-database.md`'s `products.access_rules jsonb`) — a defined, admin-visible list rather than an implicit or undocumented set of perks. |
| 10 | Community URLs are managed from the admin panel. | `communities.url` (`lms-database.md`) is a database field editable by admin — never a hardcoded link in a template. This is also what makes "eligible" honestly distinct from "actually added" (`community_access` state machine) rather than an automatic external-platform action the app can't actually perform. |
| 11 | Paid courses are separate products with independent pricing from the enrollment membership. | Reflected in `products.type = 'course'` as a distinct row/price from the `membership` product — a student can buy a course without the membership, or vice versa (subject to whatever access rules admin configures), because they're not the same catalog entry. |
| 12 | The product architecture must support future courses, course bundles, memberships, workshops, bootcamps, live classes, mentorship, digital products, and corporate training — without being built now. | `products.type` already enumerates all of these (`lms-database.md`'s Commerce section); adding one later is inserting rows against an existing type and writing that type's access-rule handler, not redesigning checkout, orders, or payments. Corporate training is flagged as likely needing an invoice-based path outside self-serve checkout (`lms-business-model.md`). |
| 13 | Payment architecture is **provider-agnostic**, via an abstraction supporting Safepay, JazzCash, Easypaisa, manual bank transfer, and future providers. | The `PaymentProvider` interface (`lms-payments.md`) means every payment path — aggregator, direct wallet API, or manual transfer — implements the same contract, so adding a provider later never touches checkout, order, or enrollment logic. |
| 14 | No provider API or merchant account is assumed to exist. Integration begins only after current documentation and actual merchant/API requirements are verified. | Confirmed by research (not assumption) in `lms-payments.md`: Stripe doesn't support Pakistan directly; JazzCash/Easypaisa both require merchant onboarding (business registration, KYC, approval) before any API credentials are issued — that approval process has its own timeline independent of any code written here. |
| 15 | Initial currency is **PKR**; the database architecture supports future currencies. | `prices.currency_code` (ISO 4217) plus the `product_id` + `currency_code` + `country_code` composite lookup (`lms-database.md`) already supports multi-currency; V1 populates only PKR rows because V1 payment processing is Pakistan-only. |
| 16 | Student authentication is separate from public marketing pages and uses secure server-side authentication. | The static marketing site has no auth surface at all (nothing to secure or breach there); all login/session logic lives in the Next.js app using server-side sessions (`lms-security.md`) — never a client-side or frontend-only auth check. |
| 17 | The admin panel has RBAC. | `roles` / `permissions` / `role_permissions` / `user_roles` (`lms-database.md`), checked server-side on every request (`lms-security.md`) — never inferred from a client-readable role claim. |
| 18 | Admin manages: students, courses, modules, lessons, enrollments, products, pricing, orders, payments, communities, announcements, certificates, coupons, analytics, settings. | Matches the admin route map in `lms-architecture.md` §3 and the capability descriptions in `lms-admin-guide.md`. Certificates and coupons are admin-manageable data models from the start even though their end-to-end feature work is V2 (see `LMS_V1_SCOPE.md`) — the schema exists now so V2 doesn't require a migration to add what V1 already modeled. |
| 19 | Student dashboard supports: My Courses, Progress, Continue Learning, Membership, Community, Orders, Certificates, Profile, Settings. | Matches `lms-student-guide.md`'s dashboard section list. |
| 20 | V1 scope is deliberately limited, documented exactly in `LMS_V1_SCOPE.md`. | Prevents "build everything at once" risk the brief itself warns against; a small, real, working product ships before the larger catalog of future revenue streams and features. |
| 21 | V2 features (certificates, coupons, bundles, live classes, advanced analytics, automated email campaigns, multiple payment providers, subscriptions, mentorship, corporate training, advanced community automation) are documented, not implemented, in V1. | Same reasoning as #20 — the schema and payment abstraction are V2-ready by design (#12, #13), so documenting V2 now costs nothing and prevents scope creep into V1's build. |
| 22 | `docs/LMS_V1_SCOPE.md` records exactly what's in and out of V1. | Created alongside this record — see that file. |
| 23 | `docs/LMS_DECISIONS.md` (this file) records every architectural decision and its reasoning. | Self-referential — this is that record. |
| 24 | `docs/LMS_IMPLEMENTATION_PLAN.md` is updated to reflect the V1/V2 phase separation. | Updated in the same round as this record — phases are now explicitly tagged V1-build or V2-documented-only. |
| 25 | Before Phase 2 starts, a full pre-flight package is delivered: architecture diagram, database/auth/payment/deployment architecture summaries, V1 scope, V2 roadmap, infrastructure estimate, security risks, migration risks, required external accounts, required environment variables, required DNS changes, required third-party services. | Delivered as `docs/LMS_PRE_PHASE_2_REVIEW.md` — a single reviewable document pulling together what's otherwise spread across the Phase 1 proposal documents, so approval to start Phase 2 is an informed decision made from one place. |
| 26–29 | No infrastructure provisioned, no production database created, no real payment credentials requested or added, no production DNS changed. | Nothing in this documentation round touches any of the four — verified true by construction, since this round is exclusively Markdown files under `docs/`. |

## Addendum — hosting decision update (2026-09-27, same session)

| # | Decision | Rationale |

| 31 | The LMS app runs on **Hostinger**, via hPanel's "Setup Node.js App" feature, at the `learn.shahidiqbal.com` subdomain you've already created (mapped to `/home/u397210942/domains/shahidiqbal.com/public_html/learn`) — **not** on a separately provisioned Railway/Render account as `lms-architecture.md` originally recommended. | You created the subdomain and chose to keep the app on your existing hosting account rather than open a new hosting relationship, once told this was an option. This doesn't reverse decision #1 (the LMS is still a separate application — separate codebase, separate process, separate directory) — it changes *where* that separate application is hosted. |
| 32 | The database (PostgreSQL) still comes from an **external managed Postgres provider** (candidates: Neon, Supabase, a database-only Railway/Render/Aiven/ElephantSQL plan) — not from Hostinger. | Hostinger shared hosting plans offer MySQL/MariaDB, not PostgreSQL. A Postgres connection string works from any host with outbound internet access, so this doesn't block running the app on Hostinger — it just means "hosting" and "database" are two different accounts either way, same as the original Railway/Render plan would also have needed to be true for the *marketing site's* hosting to stay separate. |
| 33 | Before Phase 2 provisioning, three things get verified in hPanel rather than assumed: the Node.js version(s) available, the app's memory/CPU limits, and that outbound HTTPS isn't blocked (needed to reach the external database, email provider, and payment provider APIs). | Shared-hosting Node runtimes vary by provider and plan; Next.js has a minimum supported Node version, and a resource or outbound-connection limit discovered *after* building Phase 2 would be expensive to work around retroactively. Cheaper to confirm first. |

This addendum updates `lms-architecture.md` §2/§7 and `lms-deployment.md`'s hosting section to match — both now reference this decision instead of the original Railway/Render recommendation.

## What "approved" means and doesn't mean here

Approved: the architectural direction above is the plan Phase 2 onward will build against — no further re-litigation of separate-app-vs-extend, Next.js/Postgres, the subdomain, or the V1 product list is expected before building starts.

Not approved by this record: provisioning any hosting account, creating any database (staging or production), requesting or storing any real payment credentials, changing any DNS record, or writing any application code. Those each wait for the specific gate that governs them — see `docs/LMS_PRE_PHASE_2_REVIEW.md` and `LMS_IMPLEMENTATION_PLAN.md`.
