# Technical SEO Audit — shahidiqbal.com

**Date:** 2026-10-24
**Method:** Direct inspection of source (layouts, components, content collections, config) and the built `dist/` output from `pnpm build`. **No live-site crawl, no Lighthouse/PageSpeed run, and no Search Console data were used** — this sandboxed session has no browser or live network access to the production domain, and no Search Console credentials. Where a claim below would normally come from one of those tools, this report says so explicitly instead of estimating.

## 1. Metadata

**Infrastructure:** `src/lib/seo.ts` (`pageTitle()`, `absoluteUrl()`) and `BaseLayout.astro`'s required `title`/`description`/`path` props enforce that every page passes an explicit title and description — there's no code path that silently falls back to a generic default. `pageTitle()` appends `| Shahid Security` to every non-homepage title.

**Findings:**
- **Blog**: all 41 posts (31 pre-existing + 10 added in this phase) have unique `title` and `description` in frontmatter. Verified programmatically against the built output — zero duplicate `<title>` or `<meta name="description">` tags across `dist/blog/*/index.html` (see `SEO_VALIDATION_REPORT.md` for the exact command and result).
- **Services**: all 10 service pages carry distinct `seoTitle`/`seoDescription` fields in frontmatter, separate from the on-page `title`/`shortDescription` — a deliberate separation that lets search-result copy differ from on-page headings where useful, confirmed present on the penetration-testing page and consistent across the collection schema (`z.object({ seoTitle: z.string(), seoDescription: z.string(), ... })` in `src/content.config.ts`).
- **H1 structure**: spot-checked service and blog templates — each renders exactly one `<h1>` (the post/service title via `SectionHeading as="h1"`), with H2s for body sections. No evidence of multiple-H1 pages in the templates inspected.
- **New content**: the 10 new blog posts follow the same frontmatter discipline — unique titles/descriptions, confirmed via the duplicate-check above.

**Not changed:** No existing page titles, descriptions, or URLs were altered in this phase — the brief asked to preserve meaningful existing URLs, and none needed changing for the scope of this phase (phone removal + new content, not a URL restructuring).

## 2. Canonicalization and crawlability

- **Canonical URLs**: `absoluteUrl(path)` in `seo.ts` builds canonical URLs from `site.url` (`https://shahidiqbal.com`), used consistently via each page's `path` prop. Spot-checked in built output.
- **`robots.txt`**: allows all crawling except `/api/`, `/contact/thanks/`, and `/book/thanks/` (correctly excluding only post-submission confirmation pages, not the forms themselves), and references `https://shahidiqbal.com/sitemap-index.xml`. No overly broad disallow rules found.
- **Sitemap**: generated by `@astrojs/sitemap` from the actual build output (not a hand-maintained list), so it cannot drift out of sync with real pages. Confirmed all 10 new blog URLs are present in `dist/sitemap-0.xml` after this phase's build (see `SEO_VALIDATION_REPORT.md`).
- **Trailing slashes**: all internal links observed in templates and content use a consistent trailing-slash style (`/blog/`, `/services/penetration-testing/`), matching the canonical/path convention.
- **Redirects**: not re-audited in this phase (no redirect-table changes were made) — a dedicated `verify-redirects` script already exists in `package.json`, suggesting this was addressed in an earlier SEO phase of this project; re-running it was out of scope since no URLs changed here.
- **Noindex usage**: `BaseLayout` supports a `noindex` prop, used on the `/book/thanks/` and `/contact/thanks/` pages (consistent with their `robots.txt` disallow) and not found misapplied to any indexable content page in the areas inspected.

## 3. Structured data (JSON-LD)

`src/lib/schema.ts` provides `organizationSchema()` (type `ProfessionalService`) and `breadcrumbSchema()`. Blog posts additionally render Article/FAQ-style JSON-LD wired from each post's own frontmatter (`faqs[]`, `publishedAt`, `updatedAt`).

**Findings:**
- **`telephone` field removed** from `organizationSchema()` in the prior phone-privacy work (verified still absent — see `PHONE_PRIVACY_AUDIT.md`).
- **JSON-LD validity**: every one of the 10 new blog posts' built pages contains syntactically valid JSON in each `<script type="application/ld+json">` block — verified programmatically (6 script blocks per page, all parse without error). Did not run Google's Rich Results Test or Schema.org validator against the live site, since no live URL access exists in this session; this check validates syntax and structure, not Google's acceptance of it.
- **No fabricated data**: `organizationSchema()` contains no ratings, review counts, or fabricated social proof — it maps directly to real fields in `site.ts` (name, URL, description, email, address, hours, social links) and `about.astro`'s founder data. Confirmed no `aggregateRating` or `review` properties exist anywhere in `schema.ts`.
- **Founder/organization relationship**: `organizationSchema()` links `founder` to a `Person` entity via `@id` referencing the About page, consistently with how `about.astro` presents Muhammad Shahid Iqbal — no incorporation or certification claims beyond what's stated on the About page itself (see §6 below on that page's careful certification wording).

## 4. Technical performance and accessibility

**Not independently measured in this session** — no Lighthouse, PageSpeed Insights, or real-user (CrUX) data access exists here. The honest status is:

- Image handling: Astro's built-in `image()` schema helper is used for optional blog `cover` images (none of the 10 new posts in this phase added a cover image — they rely on the shared OG-image generation pipeline (`scripts/generate-og-images.mjs`, run as part of `prebuild`), consistent with how most existing posts are set up.
- No new render-blocking resources, custom fonts, or client-side scripts were introduced by this phase's changes — the new content is pure MDX text rendered through existing templates, so it inherits whatever performance profile those templates already have.
- **Recommendation, not a finding**: if real Core Web Vitals data is wanted, the owner should pull it from Google Search Console (Core Web Vitals report) or run PageSpeed Insights directly against the live URLs — see `SEO_VALIDATION_REPORT.md` §4 for the manual checklist.

## 5. SEO content and conversion (service pages)

The 10 service pages (`src/content/services/*.mdx`) already carry a schema (`whoItsFor`, `included`, `deliverables`, `process`, `methodology`, `expectedOutcomes`, `limitations`, `faqs`) that maps closely to what the brief's Phase 3.5 asked for: problem/audience, what's included, methodology, deliverables, limitations, and a process section covering both "how to prepare" (free consultation step) and "what happens after" (report + free re-test). Spot-checked in full on `penetration-testing.mdx` — all fields populated with specific, non-generic content, including an honest limitations section ("No test, automated or manual, can guarantee a system is 100% secure").

The service page template (`src/pages/services/[slug].astro`) renders a `CTABand` at the end of each page — already updated in the prior phone-removal phase to use `mailtoLink()` ("Email us") instead of WhatsApp, so the email-first CTA requirement (Phase 8 of the brief) was already satisfied by that earlier work, not something this phase needed to add.

**Not re-audited in full for this phase**: the content quality of all 10 service pages word-by-word (time did not permit a full rewrite pass across 10 pages in addition to 10 new blog posts and the phone audit). The one spot-checked (`penetration-testing.mdx`) was already strong. If the owner wants a full content review of the remaining 9 service pages against the Phase 3.5 checklist, that's a reasonable next-phase item.

## 6. Trust and privacy content

- **About page** (`src/pages/about.astro`): credential claims are phrased carefully — "Training: CompTIA Network+ & Security+ fundamentals," "Training: Certified Ethical Hacking (CEH) methodology," "Training: CISSP domains." This phrasing describes training *in* those bodies of knowledge, not a claim of holding the CEH, CISSP, or CompTIA certifications themselves. **This is accurate as currently worded and should be preserved exactly** — rewording it to simply "CEH, CISSP, Security+" would turn an honest statement into a false certification claim. Flagged here so a future editor doesn't "simplify" it into a misstatement.
- **Experience timeline**: lists specific roles and date ranges (Cyber Security Analyst 2020–2021, SOC Analyst 2021–2023, Founder & Principal Consultant 2023–present) — specific and falsifiable rather than a vague "X years of experience" claim, which is the right pattern.
- **No testimonials or client names found** anywhere in the content inspected for this phase — consistent with the brief's instruction not to fabricate them, and apparently already the case before this phase (not something this phase needed to remove).
- **Privacy policy and responsible disclosure**: both reviewed as part of the phone-removal work this phase re-verified (see `PHONE_PRIVACY_AUDIT.md`) — both now describe data collection accurately (the booking form now collects email, reflecting the real current behavior after this phase's and the prior phase's changes).
