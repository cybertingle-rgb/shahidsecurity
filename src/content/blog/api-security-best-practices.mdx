APIs used to be called mostly by other pieces of software written by people who understood the API's intended use. That's changing. Agentic AI systems — tools that autonomously discover endpoints, chain multiple API calls together, and make decisions about what to call next — are now a growing share of real API traffic. Service-mesh measurements already show that 60–80% of API calls inside typical microservices environments are service-to-service rather than human-initiated. The risk model behind API security hasn't been thrown out because of this, but it has shifted in ways worth understanding.

## The OWASP API Security Top 10 is still the reference point

Unlike the main OWASP Top 10, which OWASP just refreshed for 2025, the [OWASP API Security Top 10](https://owasp.org/API-Security/) hasn't had a 2026 update — the current, authoritative version is still the 2023 edition. That doesn't mean it's outdated; the underlying weakness patterns it describes are structural, not tied to a particular year's threat headlines:

- **API1: Broken Object Level Authorization (BOLA).** The most common and most damaging API weakness. An endpoint checks that you're logged in, but not that the specific record you're requesting belongs to you.
- **API2: Broken Authentication.** Weak, guessable, or improperly validated tokens and credentials.
- **API3: Broken Object Property Level Authorization.** Similar to BOLA, but at the field level — you can view or edit specific fields (like a salary or an admin flag) you shouldn't be able to touch.
- **API4: Unrestricted Resource Consumption.** No limits on how many requests, how much data, or how expensive a query a single caller can make — opening the door to both abuse and denial-of-service.
- **API5: Broken Function Level Authorization.** A regular user can call an endpoint intended only for administrators, because the API doesn't check role, only login status.
- **API6: Unrestricted Access to Sensitive Business Flows.** An API technically works as designed, but nothing stops it being automated at a scale that damages the business — for example, buying out limited inventory via a purchase endpoint.
- **API7: Server-Side Request Forgery (SSRF).** The API can be tricked into making requests to internal systems on the caller's behalf.
- **API8: Security Misconfiguration.** Default settings, verbose error messages, missing security headers — the same class of issue that jumped to #2 in the 2025 main OWASP Top 10.
- **API9: Improper Inventory Management.** Old, forgotten, or undocumented API versions still running and still reachable.
- **API10: Unsafe Consumption of APIs.** Trusting data or responses from third-party APIs without validating them, the same way you'd validate user input.

## What actually changes with agentic AI callers

The list above doesn't need to change to remain relevant, but the _consequences_ of getting it wrong shift when the caller is an autonomous agent rather than a person clicking through a UI:

- **Speed and scale of exploitation increase.** A person probing for a BOLA vulnerability tests a handful of IDs manually. An agentic system can enumerate thousands of IDs in the time it takes a human to notice the traffic spike.
- **Business logic abuse (API6) becomes easier to automate at scale.** An agent designed to "complete a task efficiently" has no inherent sense that hammering a checkout endpoint 10,000 times is abusive rather than efficient.
- **Improper inventory management (API9) matters more.** Agentic systems are often given broad discovery capability — they're built to find and use whatever APIs are reachable. A forgotten, undocumented internal endpoint that was low-risk when only a handful of engineers knew it existed becomes a live target the moment something is actively scanning for reachable endpoints.
- **Unsafe consumption of third-party APIs (API10) compounds with AI supply chains.** If your application calls an AI model API, and that API's output is trusted without validation, you've effectively extended your trust boundary to a system you don't control.

Security teams surveyed on this are already uneasy: a large majority report being very concerned about AI-enhanced attacks on their APIs, and a significant share admit they aren't confident their current security investment addresses it.

## Security recommendations

- **Enforce object-level authorization on every endpoint that accepts an ID**, not just the ones handling obviously sensitive data. Assume every ID-based lookup needs an ownership check.
- **Apply rate limiting and resource quotas per caller**, not just per API key tier, so a single automated client can't exhaust capacity or abuse a business flow.
- **Maintain a real, current API inventory.** If you don't know an endpoint exists, you can't secure it, and an increasing share of attackers — human or automated — actively hunt for exactly this gap.
- **Validate responses from third-party and AI-model APIs** the same way you'd validate user-submitted input, especially before that data influences a decision or gets rendered elsewhere.
- **Test authorization logic specifically during a penetration test**, separate from authentication. A test that confirms "login works" hasn't touched most of the OWASP API Top 10.

## Key takeaways

The OWASP API Security Top 10 hasn't changed in 2026, and it doesn't need to — object-level and function-level authorization failures remain the core, structural risk. What has changed is who's calling your APIs: an increasing share of traffic comes from autonomous agents that can find and abuse a weakness far faster than a human tester or attacker could. The fix isn't a different checklist; it's applying the existing one with the assumption that whatever can be called, will be called, repeatedly and at machine speed.
